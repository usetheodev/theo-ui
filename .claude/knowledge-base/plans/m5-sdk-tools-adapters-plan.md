# Plan — M5-4 `@theokit/ui/sdk-tools-adapters` (`@theokit/ui`)

## Goal

Ship a **pure** `@theokit/ui/sdk-tools-adapters` subpath that converts `@theokit/sdk-tools` tool results (`{ok:true,...}` JSON shapes) into the prop shapes theo-ui rich primitives need (diff/code/terminal/data-table/created-files), validated by a contract test that imports the **real** sdk-tools factories and runs their handlers against temp fixtures, measured by `pnpm exec vitest run src/lib/sdk-tools-adapters/sdk-tools-adapters.test.ts` reporting all tests passed.

## Context

M5-3 shipped the `AgentToolRenderer` registry whose rich renderers only render when `part.output` already matches a structured shape (`isStructuredDiff {path,hunks}`, `isStructuredFiles {files:[{id,name}]}`, `isObjectRows`), else they degrade to `ToolCallPart` (`src/components/composites/agent-tool-renderer/agent-tool-renderer.tsx:96-110`). But `@theokit/sdk-tools` tools return JSON **strings** of shapes like `{ok:true, diff:"<unified diff>"}` (`git-diff.ts:86`) and `{ok:true, content, size}` (`read-file.ts`), which do NOT match those structured shapes — so today an sdk-tools result renders as the generic fallback.

M5-4 closes that gap: per-tool **adapter** functions that parse a tool's `{ok,...}` result and emit the exact rich-primitive props (or `null` when the result is an error / unparseable, so the caller keeps the `ToolCallPart` fallback). The adapters are **pure** and import nothing from `@theokit/sdk-tools` at runtime — they consume plain parsed objects — so `@theokit/ui` consumers gain ZERO new runtime dependency. The **contract test** (dev-only) imports the real factories via a `file:` devDep link and runs their handlers in temp dirs, proving the adapters consume what the real tools actually emit.

### Domain glossary

- **tool result** — the JSON-stringified object an sdk-tools handler returns; success is `{ok:true,...}`, error `{ok:false, error}`.
- **adapter** — pure `(result: unknown) => Props | null`; returns `null` for error/unparseable results so the caller keeps the `ToolCallPart` fallback.
- **unified diff** — the `git diff` text format (`@@ -a,b +c,d @@` hunk headers + `+`/`-`/space line prefixes) returned in `git_diff`'s `diff` field.

## ADRs

### D1 — Adapters return `Props | null`; error results yield `null`

**Decision:** each adapter is `(result: unknown) => <Props> | null`. A non-`{ok:true}` result (error, wrong shape, unparseable string) returns `null`.

**Rationale:** the caller (an M5-3 registry renderer) uses `null` as the signal to fall back to `ToolCallPart` — which already renders error state + `errorText` well (M5-3 review fix). Keeps the adapter pure + total (never throws), mirroring M5-3's defensive type-guards.

**Alternatives rejected:**
- *Throw on bad input* — forces try/catch at every call site; breaks the "never throw" contract M5-3 established. Rejected.
- *Return a partial/empty Props* — would render an empty rich surface (the exact M5-3 bug we fixed). Rejected.

### D2 — Adapters are pure and do NOT import `@theokit/sdk-tools`

**Decision:** adapters consume plain parsed objects; `@theokit/sdk-tools` is a dev-only `file:` link used solely by the contract test.

**Rationale:** theo-ui is positioned standalone with zero `@theokit/*` runtime deps (CLAUDE.md Ecosystem). A runtime import would give every consumer of the subpath a dep on an unpublished workspace package. The result shapes are stable + documented; the contract test guards against drift.

**Alternatives rejected:**
- *Runtime dep on sdk-tools* — couples the standalone UI lib to an unpublished sibling; contradicts positioning. Rejected (user decision 2026-06-21).
- *No real-factory test, fixtures only* — weaker drift protection; the user chose real factories. Rejected.

### D3 — Hand-written unified-diff parser (no new runtime dep)

**Decision:** parse `git_diff`'s `diff` string into `DiffHunk[]` with a small in-house parser (~50 LoC) targeting theo-ui's bespoke `DiffLine`/`DiffHunk` shape.

**Rationale:** no OSS diff parser emits theo-ui's `DiffHunk` shape directly (we'd wrap one anyway), and adding a runtime dep to the pure adapters would re-introduce the consumer-dep problem D2 avoids. The unified-diff hunk-header grammar (`@@ -a,b +c,d @@`) is small + stable. Rule 9 is satisfied: we are not re-implementing a general diff algorithm (git already produced the diff) — only parsing a fixed text format into a view model.

**Alternatives rejected:**
- *`parse-diff` / `gitdiff-parser` npm dep* — adds a runtime dep to the standalone lib for a 50-line parse; output still needs reshaping to `DiffHunk`. Rejected per D2 + KISS.

## Phase 2 — The 5 adapters (pure)

### T2.1 — adaptGitDiff / adaptReadFile / adaptShell / adaptListDir / adaptApplyPatch

#### Why this step

**Action:** implement the 5 adapters, each `(result: unknown) => Props | null`:
- `adaptGitDiffResult` → `{path, stats, hunks}` via `parseUnifiedDiff` (path derived from the diff header).
- `adaptReadFileResult` → `{code, language?}` (language from the path extension when present, else undefined).
- `adaptShellResult` → `TerminalLine[]` (command line from input if available; stdout→stdout lines; stderr→stderr lines; a final `ok`/`stderr` exit line).
- `adaptListDirResult` → `{columns, rows}` where rows are the entries (name, type, size).
- `adaptApplyPatchResult` → `{files: CreatedFile[]}` (one CreatedFile per patched path, `id`=path, `name`=basename).

**Reasoning:** these are the bridge M5-3 ADR D3 deferred; each maps one verified input shape to one verified target shape (ADR D1 returns `null` on error so the caller keeps `ToolCallPart`). Cited input shapes: `git-diff.ts:86`, `read-file.ts`, `shell-exec.ts:152`, `list-dir.ts:106`, `apply-patch.ts:8`.
